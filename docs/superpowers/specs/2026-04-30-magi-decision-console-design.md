# Magi 决策控制台设计稿

## 1. 产品定位

`Magi 决策控制台` 是一个面向任意问题的 AI 裁决系统。

用户直接输入问题，系统自动识别问题类型，抽取决策所需变量，交由 3 个固定决策单元分别分析，再由主控台输出 `通过`、`否决`、`延后`、`拒绝裁决` 四类结果，同时展示理由、分歧和缺失信息。

该产品不是聊天助手，不是 Agent 管理后台，不是通用问答工具。它的唯一核心目标是：`将一个问题送入三脑系统后完成一次裁决。`

## 2. 设计目标

- 建立强控制台感、强系统感、强裁决感的产品形态
- 保持一次问题一次裁决的清晰链路
- 明确区分 `信息足够时给结论` 和 `信息不足时拒绝裁决`
- 让三脑分工稳定，避免普通多角色聊天产品化
- 第一版只做最小闭环，不扩展为平台型产品

## 3. 核心概念

### 3.1 三脑结构

- `Melchior`
逻辑脑，负责逻辑、收益、成本、约束、风险判断
- `Balthasar`
人因脑，负责情绪成本、关系影响、个人承受度判断
- `Casper`
经验脑，负责经验模式、现实可执行性、相似历史判断

### 3.2 主控核心

`Magi Core` 是系统主控单元，只负责汇总裁决，不负责替代三脑重复分析。

主控职责：

- 汇总三脑倾向
- 识别冲突点
- 判断关键变量是否缺失
- 输出最终状态和一句主结论

### 3.3 裁决对象

系统不按生活、工作、商业做一级分类，直接按 `问题本身` 进入裁决。

支持的问题类型：

- `是非决策`
- `多选决策`
- `优先级决策`
- `策略决策`
- `诊断决策`

## 4. 页面结构

整个产品第一版使用单页主控台结构，分为五个区域。

### 4.1 顶部主控栏

包含以下信息：

- 产品名 `Magi 主控台`
- 当前系统状态
- 当前时间
- 裁决编号

状态文案示例：

- `QUESTION ACCEPTED`
- `ANALYZING`
- `RESOLUTION READY`

### 4.2 上方三脑区

该区域为页面视觉中心，直接参考示例图布局。

结构规则：

- 中上方为 `Balthasar`
- 左下方为 `Casper`
- 右下方为 `Melchior`
- 中央为 `Magi Core`

交互规则：

- 三脑区只显示状态和倾向，不展示长文本理由
- 每个大脑显示当前状态、当前倾向、编号、激活态
- `Magi Core` 显示当前汇总状态和最终裁决状态

视觉目标：

- 看起来像三颗并联判断的大脑
- 看起来像系统正在执行一次正式裁决
- 不做常规 SaaS 仪表盘风格

### 4.3 问题输入区

位于三脑区下方，负责接收本次裁决问题。

包含：

- 问题输入框
- 问题类型识别结果
- 开始裁决触发入口

本区只负责发起问题，不承载聊天消息流。

### 4.4 裁决总览区

用于展示主控汇总信息。

包含：

- 问题分类
- 裁决规则
- 最终结论
- 置信度
- 缺失变量

该区域优先于详细分析展示，用户应先看到最终裁决，再查看原因。

### 4.5 三脑详细分析区

位于页面下半部分，用于展开每个大脑的分析报告。

每个模块包含：

- 当前倾向
- 理由
- 关注变量
- 不确定项

展示形式采用系统报告面板，不采用聊天气泡。

## 5. 裁决机制

### 5.1 最终状态

系统只允许输出四类最终状态：

- `通过`
- `否决`
- `延后`
- `拒绝裁决`

定义如下：

- `通过`：信息足够，整体支持执行
- `否决`：信息足够，整体不支持执行
- `延后`：方向未必错误，但当前条件不成立
- `拒绝裁决`：关键变量缺失，不能负责任地下结论

### 5.2 裁决流程

1. `问题识别`
系统先判断问题类型
2. `变量完整性检查`
系统抽取本次裁决依赖的关键变量，并判断是否存在关键缺失
3. `三脑独立分析`
三个大脑分别输出独立判断
4. `主控汇总`
主控综合三脑结果后输出最终裁决

### 5.3 裁决规则

- `关键变量缺失` 拥有最高优先级
- 缺失信息足以影响结论时，系统直接进入 `拒绝裁决`
- `多数一致` 不自动等于 `通过`
- 若少数意见包含高风险否决，主控可输出 `否决` 或 `延后`
- `延后` 表示时机条件不足，而不是问题永久不可执行
- 所有最终状态都必须附带原因说明

## 6. 交互流程

第一版交互固定为单次裁决链路。

1. 用户输入一个完整问题
2. 系统识别问题类型并抽取关键变量
3. 若关键信息不足，系统先标记缺失变量
4. 三脑区进入分析态，三个大脑依次或并行亮起
5. `Magi Core` 汇总三脑结果，输出最终状态
6. 页面展示主控结论、缺失变量和三脑详细报告
7. 本次裁决进入历史记录

交互原则：

- 先判断信息是否足够，再进入裁决
- 先展示主控结论，再允许下钻查看三脑理由

## 7. 第一版功能范围

### 7.1 必做范围

- 用户注册、登录、退出
- 获取当前用户与权限能力
- 提交一个自然语言问题
- 自动识别问题类型
- 自动抽取关键变量
- 检查变量是否缺失
- 三脑分别输出分析结果
- 主控输出最终裁决
- 展示裁决依据、少数意见、缺失信息
- 按用户保存历史记录并支持回看
- 授权用户可配置个人 AI API
- 未授权用户强制使用系统 AI API

### 7.2 明确不做

- 多轮追问式对话
- 团队协作
- Agent 自定义
- 权重配置系统
- 知识库和联网检索
- 可视化流程编排
- 通用聊天助手能力

## 8. 技术架构

第一版采用前后端分离的 monorepo 架构，并通过 Docker 统一本地运行环境。

```txt
magi-console/
├─ apps/
│  ├─ frontend/
│  └─ backend/
├─ packages/
│  └─ shared/
├─ docker-compose.yml
├─ package.json
├─ pnpm-workspace.yaml
└─ tsconfig.base.json
```

### 8.1 前端项目

前端位于 `apps/frontend`。

技术栈：

- `Taro`
- `Vite`
- `Less`
- `TypeScript`

前端职责：

- 用户注册、登录页面
- 主控台页面渲染
- 问题输入与裁决触发
- 三脑状态、动效、裁决结果展示
- 历史记录回看
- 按权限展示右下角 AI 配置浮球
- 授权用户的 AI API 配置界面

前端不保存 AI API Key，不直接调用 LLM。

### 8.2 后端项目

后端位于 `apps/backend`。

技术栈：

- `Node.js`
- `TypeScript`
- `Fastify`
- `Zod`
- `Prisma`
- `MySQL 8`
- `argon2`
- `JWT + HttpOnly Cookie`
- `@fastify/cookie`
- `@fastify/rate-limit`
- `p-limit`
- `Bottleneck`

后端职责：

- 用户注册、登录、退出
- 用户权限判断
- AI API 配置读写与加密保存
- 裁决任务编排
- LLM 调用
- 并发、限流、超时、降级控制
- 裁决历史持久化

### 8.3 Docker 服务

第一版 Docker 服务：

```txt
frontend
backend
mysql
```

MySQL 连接由后端环境变量提供：

```txt
DATABASE_URL="mysql://user:password@mysql:3306/magi_console"
```

### 8.4 后端模块

```txt
apps/backend/src/
├─ modules/
│  ├─ auth/
│  ├─ user/
│  ├─ decision/
│  └─ ai-provider/
├─ config/
├─ plugins/
└─ app.ts
```

模块职责：

- `auth`：注册、登录、退出、会话鉴权
- `user`：当前用户、权限能力
- `decision`：裁决会话、三脑编排、历史记录
- `ai-provider`：个人 AI API 配置与系统 AI API 选择

## 9. API 设计

### 9.1 用户与权限

```txt
POST /api/auth/register
POST /api/auth/login
POST /api/auth/logout
GET  /api/me
GET  /api/me/capabilities
```

`/api/me/capabilities` 返回：

```json
{
  "canConfigureAiProvider": true,
  "aiProviderMode": "custom"
}
```

### 9.2 AI API 配置

```txt
GET /api/ai-provider-config
PUT /api/ai-provider-config
```

权限规则：

- 授权用户可读取、保存、启用个人 AI API 配置
- 未授权用户访问配置接口返回 `403`
- 未授权用户裁决时强制使用系统 AI API
- 授权用户启用个人配置后，裁决时优先使用个人 AI API

### 9.3 裁决会话

```txt
POST /api/decision-sessions
GET  /api/decision-sessions
GET  /api/decision-sessions/:id
```

访问规则：

- 用户只能查看自己的裁决历史
- 未登录用户不能发起裁决

## 10. LLM 并发、限流、超时和降级

### 10.1 并发控制

单个后端实例限制同时执行的裁决任务数量。

```txt
p-limit: 单实例裁决并发 5
```

### 10.2 限流控制

限流分两层：

- 接口层：限制单个 IP 和单个用户的请求频率
- LLM 层：限制单位时间内的 LLM 请求数

接口层使用 `@fastify/rate-limit`，LLM 层使用 `Bottleneck`。

### 10.3 超时控制

第一版超时规则：

- 完整裁决任务：`60s`
- 单次 LLM 请求：`25s`
- 数据库写入：`5s`
- 前端请求等待：`70s`

后端使用 `AbortController` 终止超时请求。

### 10.4 降级规则

- LLM 超时：返回 `拒绝裁决`
- 单个大脑失败：标记该大脑不可用，由 `Magi Core` 基于剩余结果输出低置信度裁决
- 三个大脑全部失败：返回 `拒绝裁决`
- LLM 返回格式错误：重试 1 次，仍失败则返回 `拒绝裁决`
- Provider 限流：返回 `429`

第一版使用同步接口，不引入队列。若后续裁决任务经常超过 `60s`，再引入 `Redis + BullMQ`。

## 12. 视觉方向

第一版界面视觉直接参考示例图，建立明确的 `系统审议现场` 感。

视觉规则：

- 黑底为主，不使用轻浮渐变
- 橙、绿、红作为核心状态色
- 块面边界明确，弱化圆润卡片感
- 强调终端、仪表盘、裁决装置质感
- 动效集中在扫描、激活、分析完成、状态切换

限制规则：

- 不做常规营销页风格
- 不做通用 AI 聊天页风格
- 不做标准后台列表页风格

## 13. 产品边界

第一版边界必须严格锁定：

- 输入只有一个问题
- 输出只有一次裁决
- 三脑角色固定不可配置
- 用户必须登录后才能发起裁决
- 普通用户不能配置个人 AI API
- 授权用户通过右下角浮球进入 AI API 配置界面
- AI API Key 只允许后端加密保存
- 系统核心对象始终是 `当前问题的一次裁决过程`
- 产品不扩展为 Agent 管理台
- 产品不扩展为通用问答工具

## 14. 成功标准

若第一版设计正确，用户打开页面后应立即理解：

- 这不是聊天工具
- 这是一个把问题送进三脑系统里进行裁决的主控台
- 上方三脑是核心视觉记忆点
- 下方分析区是对本次裁决的展开解释
- 系统可以明确给答案，也可以因为信息不足而拒绝裁决
- 系统支持登录后的个人历史记录
- 只有授权用户可以配置个人 AI API
